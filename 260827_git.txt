Open API

API -> 기관에 데이터를 주기로 하고 만든 공식 창고
* 화면을 위한 HTML이 아니라 프로그램을 위한 데이터 돌려줌
* 구조가 문서로 약속돼 있어 바뀌지 않음

크롤링 API 차이
	크롤링	Open API
합법성	약관 확인 필요	명시적으로 허용됨
안정성	구조가 바뀌면 깨짐	버전으로 관리됨
속도	파싱 비용 있음	빠름
데이터 범위	화면에 보이는 전부	제공하기로 한 것만
제약	차단 위험	쿼터 제한
APi 문서 읽는 순서
01	엔드포인트	요청을 보낼 주소. 기능마다 다릅니다.
02	요청 변수	필수와 선택. 인증키 페이지 조회 조건이 여기 있습니다.
03	출력 결과	응답 필드의 이름과 뜻. 무엇을 쓸지 미리 골라둡니다.
04	에러 코드	키 오류•쿼터 초과 파라미터 오류를 구분해 처리해야 합니다.
인증 방식
- API KEY 
* 발급받은 키를 함께 보낸다. (쿼리 파라미터나 헤더에 실어 보냄)
- TOKEN 
* 로그인 후 토큰을 받는다. (헤더의 Authoeization에 넣음) 만료되면 갱신
- OAUTH
* 사용자 대신 권한을 받음 (개인 데이터에 접근할 때 쓰는 방법)

키 관리
- 코드에 API키 적으면 안됨 
- API키는 .env 파일에 적은 후 .gitignore 에 등록 후 깃허브에 올라가지 않게 처리

서비스키 인코딩 
# 포털은 키를 두 벌 줍니다
# Encoding : abcd%2Bef%2F1234%3D%3D 	(URL 인코딩된 것)
# Decoding : abcd+ef/1234==				(원본)
# requests의 params=는 값을 알아서 인코딩
#-> Decoding 키를 넣어야 함
params = ("serviceKey": DECODING_KEY, "numOfRows": 100}
r = requests.get(URL, params=params)
# URL 문자열에 직접 붙일 때만 Encoding 키를 씀

* Encoding 키를 params에 넣으면 이중 인코딩돼 인증 실패

응답 구조와 오류
- HTTP 200인데 실패인 경우 있음

대표적인 resultMsg
# SERVICE KEY IS NOT REGISTERED ERROR
# LIMITED NUMBER OF SERVICE REQUESTS EXCEEDS
# NO MANDATORY REQUEST PARAMETERS
* 응답 본문의 resultCode를 확인 해야함

전체 페이지 순회
- totalCount를 읽어 반복 횟수 계산
* items가 1건일 대 리스트가 벗겨지는 함정이 있음
* totalCount가 없으면 빈 응답이 종료조건
* 무한 루프 방지 => 최대 페이지 상한 조건 있어야함

쿼터 안에서 설계
- 개발 계정은 하루 10,000건
* 조회 단위를 잘게 쪼개면 호출 수가 곧바로 쿼터를 넘김
* numOfRows 키워 한 번에 많이 받는 것이 유일한 해법

중첩 구조 접근
- Preview 트리를 그대로 대괄호로
* 리스트가 나오면 반복문, 딕셔너리가 나오면 키 접근
* .get()은 키가 없어도 오류 대신 기본 값을 돌려줌

OPEN API & DATABASE
원본을 남김
- 파싱한 결과만 저장하면 나중에 되돌릴 수 없음
* 파싱 로직은 반드시 바뀜 - 필드가 더 필요해 지거나 버그를 발견
* 수집은 비싸고 되돌릴 수 없음 -> 파싱은 싸고 다시 할 수 있음
* 응답 원문 함께 보관 -> 파싱 결과는 파생물로

RDB
 자주쓰는 컬럼 타입
타입	쓰는 곳	비고
BIGINT	고유 번호, 큰 정수	AUTO_INCREMENT와 함께
VARCHAR(n)	짧은 문자열	길이를 정해야 함
TEXT • LONGTEXT	본문, 응답 원문	인덱스를 걸기 어려움
DATE • DATETIME	날짜, 일시	문자열로 담지 말 것
DECIMAL (p, s)	금액, 정확한 수치	FLOAT는 오차가 생김
CHAR(n)	해시처럼 길이 고정	VARCHAR보다 빠름

PK | UNIQUE | 인덱스
PRIMARY KEY - 행을 식별
* 테이블당 하나, 중복도 NULL도 허용X (의미 없는 일련번호 사용)
UNIQUE - 중복을 막음
* 여러 개를 걸 수 O ( 고유 키에 거는 것이 핵심)
INDEX - 찾기를 빠르게 함
* 중복을 막지 X (WHERE에 쓰는 컬럼에 검)

테이블 만들기
- 수집 결과를 담을 표를 정의
* Utf8mb4 -> 이모지까지 안전하게 담김
* UNIQUE는 제약이자 인덱스라 중복 검사도 빨라짐
* payload에 응답 원문을 통째로 넣어 원본 보존

조회와 집계
- 현황을 보는 가장 기본적인 쿼리
* SELECT * => 확인용, 코드에서는 컬럼 명시
* WHERE에 쓰는 컬럼에 인덱스가 있어야 빠름
* GROUP BY => 수집 현황 결측률 집계의 기본 도구

JOIN
- 두 표를 키로 연결
* 조인 키의 타입과 형식이 같아야 붙음
* LEFT JOIN 결과에 NULL 많음 => 키가 안맞음

인덱스 대가
- 조회는 빨라지지만 삽입은 느려짐
* 인덱스는 별도의 정렬돈 구조를 함께 유지
* 행을 넣을 때마다 그 구조도 갱신되므로 삽입이 느려짐 
* 대량 적재 전에 인덱스를 잠시 빼두는 것도 선택지

적재
파이썬에서 연결
- charset을 utf8mb4로 지정X => 한글 깨짐
- 비밀번호도 .env로 관리
- finally에서 close를 보장해서 커넥션 안샘

UPSERT
- 데이터가 없으면 insert, 이미 있으면 update
* 중복 데이터를 계속 쌓지 않고 최신 상태를 유지하고 싶을 때 사용

ON DUPLICATE KEY UPDAT
- insert하려고 했는데 unique 키나 pk가 이미 존재하면 update로 바꿔서 처리하라
# DUPLICATE KEY -> pk 또는 unique 제약조건에 걸리는 중복

executemany 배치삽입
- 여러 행을 한 번에 묶어서 실행하는 방식

API 응답을 원문 그대로 담기
- 가장 기본적인 코드 형태
* 같은 스크립트를 두 번 돌려 행 수가 그대로인지 반드시 확인
* ensure_ascii = False여애 한글이 그대로 보관
